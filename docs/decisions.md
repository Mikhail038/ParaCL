## 1. Проект целиком на C++20-модулях

**Статус:** принято (требование задания HW7.1)

**Контекст.** Задание требует module-based проект.

**Решение.**
- Каждая логическая часть компилятора — отдельный модуль (`export module paracl.xxx;`).
- Сторонние и стандартные заголовки подключаются только в global module fragment
  (участок между `module;` и `export module ...;`):

  ```cpp
  module;
  #include <vector>
  export module paracl.parser;
  ```

- Не используем `#include` внутри purview (тела модуля) и `import <header>;`
  (header units).
- Граф импортов без циклов.

**Обоснование.** Лекция 07, слайды 61, 65, 66: `#include` в purview ломает
привязку сущностей к модулям, header units тянут за собой состояние макросов.
Циклический импорт модулей запрещён стандартом (слайд 56).

## 2. Фронтенд проверяет, бэкенд исполняет

**Статус:** принято

**Контекст.** В tree-walking интерпретаторе (интерпретаторе, который рекурсивно
обходит дерево и сразу вычисляет) соблазнительно проверять типы прямо во время
исполнения.

**Варианты.**

| Вариант | Как работает |
|---|---|
| A. Проверки внутри интерпретатора | типы проверяются, когда до узла дошло исполнение |
| B. Отдельный проход до запуска | вся программа проверяется целиком, потом исполняется |

**Решение.** Вариант B. Фронтенд (лексер, парсер, проверка типов) не исполняет
программу. Бэкенд (интерпретатор или генератор IR) не проверяет её.

**Обоснование.**

```pcl
x = input(0) : int;
if (x == 42) {
  s = glue(1, 2);
  y = s + 1;        // ошибка типов: структура + число
}
```

- При варианте A ошибка найдётся, только если пользователь введёт 42. Язык
  статически типизирован, поэтому ошибка должна находиться до запуска, как у `gcc`.
- Генератор IR программу не исполняет. Все проверки, спрятанные в интерпретаторе,
  при переходе на IR пропали бы.

**Следствие.** Фронтенд не пытается узнать значения переменных. Размер
`repeat(v0, n)` при `n` из `input` неизвестен до запуска. Фронтенд помечает его
как «известен при запуске», но не вычисляет. Проверки формы выражения допустимы:
например, «индекс у `vector` — литерал».

## 3. Проверка типов выдаёт полностью разрешённые типы

**Статус:** принято

**Контекст.** Бэкенду нужно знать, какую операцию выполнять. Пример: `v2 + 1` при
`v2 : int(16)`.

**Варианты.**

| Вариант | Как работает |
|---|---|
| A. Типы в рантайме | каждое значение носит тег, `add` решает по тегам во время выполнения (как Python) |
| B. Типы при компиляции | каждый узел дерева заранее подписан конкретным типом (как C) |

**Решение.** Вариант B. После проверки типов у каждого выражения есть конкретный
тип: `int(16)`, а не «какой-то int». Все неявные преобразования становятся явными
узлами `Convert`.

**Обоснование.**
- В IR инструкция выбирается при генерации: `add i16` или `add i32`. Узнать это
  при запуске уже поздно.
- Интерпретатору вариант B не мешает, а только упрощает его: решения уже приняты.

**Пример.**

```pcl
v0 = 0;
v1 : double = v0;
v2 : int(16) = 5;
v3 = v2 + 1;
```

После проверки типов:

```
Assign v1
└─ Convert int(32) → double     ← узел вставлен проверкой типов
   └─ Var v0 : int(32)

Assign v3
└─ Add            : int(16)
   ├─ Var v2      : int(16)
   └─ Const 1     : int(16)
```

Бэкенд, увидев `Convert`, делает `static_cast<double>` (интерпретатор) или
`sitofp` (инструкция IR «signed int → float»).

Для массивов то же самое: `int[5]` (размер известен) и `repeat(v0, n)` с `n` из
`input` (VLA, размер известен при запуске) помечаются по-разному.

## 4. Generic-функции раскрываются во фронтенде

**Статус:** принято

**Контекст.** У generic-функции типы параметров неизвестны до вызова:

```pcl
f1 : (x) = { v3 = x + 1; v3 * v3; };
a = f1(2);      // x — int
b = f1(2.5);    // x — double
```

**Варианты.**

| Вариант | Как работает |
|---|---|
| A. В бэкенде | интерпретатор выполняет тело с любыми значениями, генератор IR сам плодит копии |
| B. Во фронтенде | проверка типов создаёт отдельную копию функции под каждый набор типов аргументов |

**Решение.** Вариант B (так же устроены шаблоны C++). На каждом вызове проверка
типов:

1. берёт ключ `(имя функции, типы аргументов)`, например `(f1, [int])`;
2. если такой копии ещё нет, клонирует тело и проверяет его с конкретными типами;
3. переписывает вызов на конкретную копию.

Бэкенд видит только обычные функции:

```
f1<int>(x: int) -> int          { ... }
f1<double>(x: double) -> double { ... }
a = call f1<int>(2)
b = call f1<double>(2.5)
```

**Обоснование.**
- Раскрытие написано один раз, а не в каждом бэкенде.
- IR требует конкретных сигнатур: `define i32 @f1_int(i32 %x)`.
- Ошибка вроде `f1(glue(1, 2))` находится при компиляции (см. решение 2).

**Известная сложность.** Рекурсивный generic
(`f4 : (x) = { if (x < 2) return 1; x * f4(x - 1); };`): при проверке `f4<int>`
встречается вызов той же копии, возвращаемый тип которой ещё не выведен.
Способ решения — открытый вопрос.

## 5. Выбор бэкенда отложен, граница — типизированное AST

**Статус:** отложено (решить к концу MVP фронтенда, ~середина ноября 2026)

**Контекст.** По условию нужен интерпретатор, LLVM IR даёт бонус.

**Варианты.**
- Только интерпретатор.
- Только LLVM IR, исполнение через `lli` или `clang file.ll`. Нужно уточнить у
  преподавателя, засчитывается ли это.
- Оба бэкенда (по одному на человека) и дифференциальное тестирование:
  одна программа должна давать одинаковый вывод в обоих.

**Решение.** Отложить. Фронтенд проектируем так, чтобы он подходил для любого
варианта: решения 2, 3 и 4 это обеспечивают.

**Граница.** Фронтенд отдаёт бэкенду типизированное AST с такими гарантиями:

1. У каждого выражения есть конкретный тип.
2. Все неявные преобразования — явные узлы `Convert`.
3. Каждый вызов указывает на конкретную, не generic, функцию.
4. Программа проверена: ошибок типов в ней нет.

## 6. Парсер — рукописный рекурсивный спуск

**Статус:** предложено

**Варианты.** Bison/Flex или рукописный рекурсивный спуск.

**Аргументы за рукописный.**
- Bison и Flex генерируют заголовки и макросы. С модулями это стыкуется только
  через обёртки в global module fragment.
- Грамматика неоднозначна: `:` означает аннотацию типа, имя поля в `glue` или
  диапазон `0:5`; `{` открывает блок, тип структуры или инициализатор. В рукописном
  парсере это решается заглядыванием на токен вперёд, в Bison — конфликтами грамматики.
- Опыт есть (MY_Language: `get_Expression → get_AddSub → ...`).

## 7. Если IR — сначала текстовый `.ll`

**Статус:** предложено (имеет смысл, только если выберем IR)

**Варианты.** Печатать текстовый `.ll` или использовать C++ API LLVM (`IRBuilder`).

**Аргументы за текст.**
- Не нужна зависимость: `llvm-devel` не установлен, а `clang`, `lli` и `llc` уже есть.
- Не нужно тащить тяжёлые заголовки LLVM в модули.
- Результат легко читать и сравнивать в тестах.
